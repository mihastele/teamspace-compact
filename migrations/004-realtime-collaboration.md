# 004 — Versioned Yjs collaboration and ephemeral presence

2026-10-04. Additive, lazy trusted migration; no live database changed.

POST `notes/:id/collaboration` promotes a legacy note exactly once in a member-authorized transaction. Existing text/type/metadata are retained; each block obtains a stable UUID. The note gains `collab: {version:1,generation:UUID,state:base64YjsCheckpoint,sequence:integer}` and `metadataRevision`. Maintained TypeScript models are the schema types; Firestore has no generated model types. Notes remain member-readable/server-writable. Old whole-content PATCH requests are fenced after promotion; metadata PATCH uses metadataRevision independently of content acknowledgements.

Update requests bind authenticated UID, generation, operation UUID and binary payload digest. The server reauthorizes membership, checks the live note, merges the update transactionally, validates schema/permanent tombstones and dependency completeness, materializes content, and increments sequence/revision. A bounded checkpoint and materialized content are rewritten atomically: document-level contention is explicit, but stale checkpoints cannot overwrite concurrent work. Combined serialized state/content are bounded below Firestore's 1MiB document ceiling (800KB with metadata headroom); binary/update limits are separately enforced. No automatic compaction resets IDs or generations. Very long editing histories can reach the explicit limit and require export/recovery rather than losing work. This foundation targets small workspaces, not unbounded team scale.

Private `notes/:id/collaborationReceipts/:hash(uid:operationId)` documents contain only authenticated identity, generation, operation UUID, digest, committed sequence and server commit time. They have no TTL: arbitrary delayed retries must remain idempotent. Reused operation IDs with different payloads fail. Deleting a note first fences writes, removes attachment bytes and recursively removes receipt/presence subcollections before deleting the parent (failed cleanup leaves a fenced, retryable parent). Firestore does not cascade. Workspace/account deletion tooling must likewise recursively remove these collections. Do not remove receipts or replace generations during maintenance without a separately verified replay policy.

Member-readable/server-writable `notes/:id/presence/:hash(uid:sessionId)` leases contain uid, sessionId, membership-derived displayName, server lastSeen and server expiry (90 seconds). Clients heartbeat at 45 seconds, filter expired leases and remove their own session on exit when possible. Presence is approximate and never establishes durability; crashes may appear online until expiry. Rate limit 10 presence mutations per user/minute. Firebase Realtime Database was evaluated: native disconnect is preferable for exact presence, but cross-store membership authorization and additional provisioning are unnecessary for this bounded approximation. Presence expiry TTL is best-effort garbage collection, not UI validity or content data retention. TTL never applies to receipts.

Deploy rules/index overrides and trusted routes before the new client. Index exemptions for large `content`/`collab` maps avoid unused index entry inflation; existing note parent queries remain indexed. Presence reads require membership and a live parent note; all browser writes remain denied; receipt reads/writes default-denied. Rollback to an old client cannot edit promoted content: retain new trusted backend/read state or export materialized content before a deliberate offline migration. Do not silently flatten or discard CRDT history.

Workspace exports use materialized note content with stable IDs and may include collab state for faithful recovery; presence and private receipts are operational and excluded from ordinary user content exports. User-visible Markdown export remains plain materialized content. Deletion removes content, checkpoints, receipts, leases and existing attachments; tombstones belong to the checkpoint, not a new user-data table.

Clean emulator fixtures and trusted API/rules tests verify promotion, legacy fences, concurrency final states, replay, membership/outsider/revocation, dependency/size rejection, presence expiry identity and parent deletion cleanup. A live deployment still requires Firebase provisioning and two-browser acceptance.
