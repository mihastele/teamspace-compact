# 005 — Page history and restore

Additive, lazy schema; no live database has been modified. Apply the committed Firestore index/TTL configuration before release. Existing pages need no backfill: their first subsequent edit creates a checkpoint. A clean emulator suite creates all shapes from scratch; TypeScript models are maintained manually because Firestore has no generated schema types.

Each note may contain `historyCheckpointAt` (server timestamp). `historyVersions/r{sourceRevision}` holds an immutable title/content snapshot, sourceRevision, capturedAt, capturedBy, capturedName, kind (`checkpoint`, `named`, `before_restore`), name, and expiresAt. Automatic checkpoints are captured atomically with the first save and then at most once every five minutes of activity, using the trusted server clock. They expire after 30 days. Expired snapshots are immediately unavailable through the API even before asynchronous TTL deletion. Named versions are permanent (`expiresAt: null`); naming an automatic snapshot promotes only its label/retention, never replaces its captured content. The note revision is the identity, not a client timestamp. No idle timer creates checkpoints.

Restores preserve parent/children, attachments, and shared-board tasks. A transaction reauthorizes membership, compares the current global revision, backs up the current title/content unless already captured, and replaces title/content using a fresh validated Yjs generation. Old-generation edits are rejected for explicit recovery. `historyRestores/{sha256(uid:operationId)}` permanently records payload-bound retry receipts. Replays acknowledge the current note without restoring twice. Receipts have no TTL because removing them would permit old operations to run again. Checkpoint writes and all restore reads occur within the note transaction before mutations.

Both subcollections remain default-denied to browser SDK reads/writes; only member-authorized trusted APIs expose versions. Notes remain member-readable and server-writable. Naming/restoring are limited to ten requests per authenticated user per minute each. List responses omit content and read at most 21 projected records, with revision cursors allowing bounded scanning past expired records. No new composite index is required; sourceRevision uses its single-field index. Exempt content from indexing and enable historyVersions.expiresAt TTL.

Export: include unexpired historyVersions snapshots in future complete workspace export; Markdown download still exports only current title/content. Include named snapshots and distinguish their retained labels. Private historyRestores receipts are operational metadata and are not user-document exports. Full workspace export is still an open product feature.

Deletion: the existing live-note fence blocks new history/restore mutations. Recursive cleanup removes both subcollections before the parent; failed cleanup leaves a fenced retryable parent. Deleting a note therefore deletes permanent versions and receipts as well. No external attachment/task deletion is added by restore. Future account deletion must preserve existing workspace-owned version history until workspace/page deletion, subject to the eventual account-data retention policy.

Rollout: deploy index/TTL configuration, trusted API, then compatible client UI. Old collaborative clients recover stale-generation edits; old legacy clients fail revision checks. Rollback should disable restore/naming UI before old server deployment, retain history data, and never roll back note state or generation wholesale. History storage grows with content size and named-version count; no named-version quota is introduced in this iteration.
